## 0. MASTER VISION (Persistent Context — Always Apply)

### Who You Are
You are an expert full-stack developer, software architect, and technical SEO specialist. You write **clean, modular, well-documented, production-quality code**. You ask before running initialization commands or making irreversible changes.

### What We're Building
**"Wayka"** — an artisanal catering, sweets, and frozen-product retail business in **Costa Rica**. The website must feel **warm, human, familiar, and artisanal** — never cold, corporate, or "Amazon-like." The identity is rooted in organic, rustic, ancestral values (see `wayka.pdf`).

### Non-Negotiable Principles (apply to everything)
1. **Minimum clicks, minimum scrolling** — the client's core UX rule.
2. **Mobile-first** — most Costa Rican traffic is mobile.
3. **SEO & performance are first-class concerns** — server-rendered HTML, optimized Core Web Vitals, Spanish-language local SEO.
4. **Accessibility** — WCAG AA contrast and semantics.
5. **No payment gateway** — all orders funnel to **WhatsApp** with structured, human messages.
6. **Client-manageable** — the business owner manages all content via django-admin without touching code.
7. **Measurement is built-in, not bolted-on** — every WhatsApp redirect is a tracked conversion event from day one. Analytics must be privacy-conscious and lightweight (no impact on Core Web Vitals).

- **Frontend:** Next.js (React, **App Router**, Server Components + Metadata API) + Tailwind CSS + Framer Motion.
- **Backend:** Django + Django REST Framework (DRF) + Python.

- **Media (Phase 1):** local Django media root (no cloud storage yet).
- **Analytics:** GA4 (custom events) + Google Search Console + Microsoft Clarity. Meta Pixel deferred unless ads are confirmed.

## P2 — Data Models, States & Admin (Backend Core)

**Goal:** The full content model with lifecycle states and portion variants, fully manageable in django-admin.

### Models

**`Product`**
- `name`, `description`, `category` (choices: `bocaditos`, `sweets`, `pizzas`)
- **`status`** (choices):
  - `active` — visible **and** orderable (shows "Pedir Ya" / "Añadir a mis antojos")
  - `coming_soon` — visible, shows **"Próximamente"** badge, ordering **disabled**
  - `sold_out` — visible, shows **"Agotado"** badge, ordering **disabled**
  - `inactive` — **hidden** from the website entirely (admin-only)
- `display_order` (integer) — controls order within category
- `is_featured` (boolean) — optionally pin to top of category
- `image`
- **SEO fields:** `slug` (auto-generated from name, unique), `meta_description`, `alt_text`
- **No single price here** — price lives on variants.

**`ProductVariant`** (portion sizes — included in MVP)
- `product` (FK, `related_name="variants"`)
- `name` (e.g., "Pequeña", "Mediana", "Familiar")
- `price` (DecimalField, in CRC ₡)
- `is_default` (boolean)
- `is_available` (boolean) — **per-variant availability** (a "Familiar" can be sold out while "Mediana" is available)
- `display_order` (integer)

**`Supermarket`**
- `name`, `address`, `province`/`canton`, optional geo-coordinates.

### Business Rules
- A product with **one** variant → frontend shows the price directly, no size selector.
- A product with **multiple** variants → frontend shows a size selector; user must choose before adding to the Antojo Cart.
- **Sort logic:** within a category, order by `is_featured` (featured first), then `display_order`. **Unavailable items (`coming_soon`, `sold_out`) sort to the bottom.**

### Admin
- Customize django-admin so the client manages everything code-free.
- **Drag-and-drop reordering** for `display_order` if feasible (e.g., `django-admin-sortable2`); otherwise an editable order field.
- Inline editing of `ProductVariant` within the `Product` admin page.
- Clear Spanish labels for status choices.

### Tests (Phase 2)
- Model tests: slug auto-generation & uniqueness; status choices; variant relationships.
- Business-logic tests: sort ordering (featured first, unavailable last); single-vs-multi variant detection.
- Admin smoke test: product + inline variants save correctly.

**✅ Stop and confirm before P3.**

## P3 — REST API & SEO Data Layer

**Goal:** Clean, documented API endpoints that power the frontend and feed SEO metadata.

### Endpoints
- `GET /api/products/` — public catalog. **Excludes `inactive`.** Supports `?category=` filtering. Returns nested variants. Sorted per the rules in P2.
- `GET /api/products/<slug>/` — single product detail (by slug, for SEO-friendly URLs).
- `GET /api/supermarkets/` — store locations.

### Serializer Requirements
- Each product returns its `status`, `is_featured`, all SEO fields, and nested available variants.
- Expose a computed `is_orderable` flag (`true` only when `status == active`) so the frontend doesn't re-implement the rule.
- Prices serialized in CRC ₡ format.

### Tests (Phase 3)
- API tests: `inactive` products never appear; category filter works; ordering is correct; slug lookup works; `is_orderable` is accurate for each status.
- Serializer tests: variants nest correctly; SEO fields present.

**✅ Stop and confirm before P4.**

## P4 — Frontend Experience (The Heart of Wayka)

**Goal:** The warm, human, low-friction UX — built mobile-first with full theme support.

### 4.1 Home / Landing
- Visual hero with welcoming, **SEO-friendly Spanish bio**.
- Animated theme toggle (from P1).
- Above the fold (minimal scroll): **2 clear navigation views** separating **B2C catalog** from the **B2B event planner**.

### 4.2 B2C Catalog Tabs
Three instant-switching tabs (no page reload), each also reachable via a crawlable server-rendered URL for SEO:
1. **Bocaditos**  2. **Sweets**  3. **Pizzas**

### 4.3 Product Cards (state-aware)
- Render badges based on `status`: "Próximamente", "Agotado".
- **"Pedir Ya"** and **"Añadir a mis antojos"** buttons appear **only when `is_orderable`**; otherwise disabled/hidden.
- Size selector appears only when multiple variants exist; respects per-variant `is_available`.

### 4.4 "La Bolsa de Antojos" (Antojo Cart)
- Drawer/modal, theme-aware, conversational tone (e.g., *"Te estás llevando un excelente combo, ¡te va a encantar!"*).
- "Pedir Ya" instantly opens the cart with that item.
- Cart line items show selected variant (e.g., "Pizza Artesanal (Familiar)").
- **Final CTA → WhatsApp redirect** (no payment). Build a dynamic URL with a structured, human message:
  > *"¡Hola Wayka! Me gustaría coordinar el pedido de estos antojos:\n- 2x Pizza Artesanal (Familiar)\n- 1x Pie de Limón\n¿Me ayudan a coordinar el envío?"*

### 4.5 B2B Event Planner & Catering Calculator
- Inputs: **event type** (Corporate, Birthday, Family Gathering) + **number of guests**.
- Logic: recommend catering volume (e.g., 5 snacks/guest).
- CTA: **"Coordinar este menú por WhatsApp"** — forwards the calculation details to WhatsApp.

### 4.6 Analytics Wiring (foundational — build the utility now)
- Create the centralized analytics utility (`lib/analytics.ts`) per **Section 8**. All CTAs built in this phase (Pedir Ya, Antojo Cart, calculator) must call it — **never call `gtag` directly.**

### Tests (Phase 4)

- Cart tests: add/remove items, quantity, variant selection, **correct WhatsApp URL/message generation**.
- Calculator tests: correct volume math; correct WhatsApp message.
- Theme test: cart and cards render correctly in both modes.
- Analytics test: each CTA calls the analytics utility with the correct event + parameters (mock the utility).

## 8. Analytics Event Specification

> Implement a single, centralized analytics utility (e.g., `lib/analytics.ts`) that wraps `gtag`. **All components must call this utility — never call `gtag` directly.** This keeps tracking consistent, testable, and easy to extend.

### Core Conversion Event

**`whatsapp_order_click`** — fires on **every** WhatsApp redirect.

| Parameter | Type | Description | Example |
|---|---|---|---|
| `source` | string | Which CTA triggered it | `pedir_ya` \| `antojo_cart` \| `catering_calculator` |
| `item_count` | number | Number of distinct items | `3` |
| `total_quantity` | number | Sum of all quantities | `5` |
| `category` | string | Dominant/primary category | `pizzas` \| `sweets` \| `bocaditos` \| `mixed` |
| `estimated_value_crc` | number | Total estimated value in ₡ | `12500` |

### Supporting Engagement Events

| Event | When it fires | Key parameters |
|---|---|---|
| `view_product` | Product card/detail viewed | `product_slug`, `category`, `status` |
| `add_to_antojos` | "Añadir a mis antojos" clicked | `product_slug`, `variant_name`, `price_crc` |
| `open_cart` | Antojo Cart drawer opened | `source` (`pedir_ya` \| `manual`), `item_count` |
| `remove_from_antojos` | Item removed from cart | `product_slug`, `variant_name` |
| `select_variant` | Size/portion selected | `product_slug`, `variant_name` |
| `category_tab_switch` | B2C tab changed | `from_category`, `to_category` |
| `calculator_used` | B2B calculator produces a result | `event_type`, `guest_count`, `recommended_items` |
| `theme_toggle` | Light/Dark switched | `to_theme` (`light` \| `dark`) |

### North-Star Funnel
```
view_product → add_to_antojos → open_cart → whatsapp_order_click → [confirmed order — off-site]
   (GA4)          (GA4)           (GA4)          (GA4)              (WhatsApp labels + sales log)
```

> **Off-site closing the loop (manual, not code):** Wayka uses **WhatsApp Business labels** ("Nuevo pedido", "Cotización", "Cerrado") + a simple sales log to record actual confirmed orders and ₡ value. GA4 measures intent up to the WhatsApp click; the WhatsApp side measures the real outcome. Document this clearly in the README so the client understands the two halves.
